## 质量复核与瓶颈

串行的空文响应出现了引体向上、器械划船、高位下拉及重量次数。它通过结构校验，但失败于“无训练动作”的事实检查点。这证明只测合法 JSON 或 HTTP 成功率会让编造结果获得虚假优势，当前提示词也需要下一阶段单独验证。

检查点本身经过一次修正：初版要求训练记录拆成固定 groups，误判了合法的 repsList；同时对于末尾带 `➕` 的次数表达，不能要求模型补出组数。最终使用 69 个检查点：已知组数通过现有校验器展开集合检查重量/次数；未知组数保留 reportedReps；非训练记录按总动作数检查，允许合法空 session。UNKNOWN、缺失组数与核对提示没有直接判成错误。修正没有改变模型回答或生产校验器，`quality-audit.json` 用原 trace、来源及回答指纹记录复核关系。主试跑最终为 7/8 与 8/8；通过仅代表这些有限检查点，不等于完整标注集准确率。动作名字和顺序仍需人工核查。

串行批次 HTTP 合计 150.040 秒，解析校验合计 18.536 毫秒，写入阶段 58.913 毫秒。约 99.9% 的此批次时间落在 HTTP 阶段。HTTP 包括网络与完整模型响应，不能进一步断言服务端推理占比。并发 2 的 HTTP 合计 143.316 秒、配额等待合计 150.996 秒；它们在任务间重叠，不能相加预测 90.056 秒的批次时间。写入阶段包含 benchmark 私有回答落盘与 Room；同步事件记录的成本没有扣除。数据库初始化另记，c1 为 48.807 毫秒、c2 为 41.600 毫秒，不在上述调度后批次计时内。

c1/c2 都有 8,334 prompt tokens，输出分别为 8,297 / 8,190 tokens；缓存 tokens 分别为 1,344 / 2,240。短日记下固定提示词、输出长度及缓存都值得实验，但没有改变本次协议。非流式 TTFT 为不适用，首次结果时间以持久化、来源复核和质量检查通过为边界；堆内存只是结束快照。

## 可行性、故障与验证边界

ADK 1.3.1 的真实 Runner 已编译、通过请求一致性/隔离/取消回放。线上发现 history rewriter 删除空白 user turn，已在自定义 Model 桥接处恢复冻结空文；离线测试确认一次请求和相同正文哈希。修复后没有再发付费 ADK 请求，因此没有修复版完整线上成绩。

原生 ADK 集成还遇到资源索引、桌面 XML parser 重复及未使用 Google GenAI client 的旧 Ktor ABI；处理限定在 benchmark。R8 的 `-checkdiscard` 验证该 client 被删除，FitLog 的 Ktor 没有降级。内置 Google provider 未验证。OpenMinis 的 Android loop 仍与大型 ViewModel 私有状态耦合，没有独立可运行库，因此只报告集成障碍。pi 是固定 npm 1.1.0 的实际 Agent 回放，Android JS 引擎和桥接尚未实现。源码依据及固定版本见 [RESEARCH.md](RESEARCH.md)。
