# 2026-10-11 Android 真实 runtime 比较

在 OPPO PGEM10 / Android 16 上完成了 ADK 1.3.1 自定义 Model 桥接与轻量 Kotlin 的完整线上配对批次：相同并发 2、同一八篇、每篇一次模型调用，共 16 次，两者均八篇通过现有事实检查点。真实尝试累计 **108 次**，无自动重试。ADK 此批次耗时较低，但只有一个时段，尚未通过速度置信区间门槛；生产仍保留直接调用，没有最终 runtime 赢家。

## 控制与实机状态

- 模型 `zai-org/glm-5.3-flash`，端点 `https://api.ppio.com/openai/v1/chat/completions`。
- 提示词 `diary-json-v3`、校验器 `diary-basic-v2`，冻结八篇及 69 个事实检查点；每篇独立上下文、一次调用、无工具循环。
- 两者使用同一个 canonical Ktor/OkHttp 客户端、输出协议、解析器和隔离 Room；连接超时 15 秒、配额接纳后的请求超时 120 秒，完整响应读取包含在内。
- 种子 43 的配置顺序为 ADK、轻量。逻辑日记列表相同；协程实际到达请求配额入口的顺序不同，原 trace 和核验 sidecar 保存实际顺序。这是本轮完整调度链的观测，不能当成相同 HTTP 接纳顺序下的纯框架开销实验。
- USB 连接、解锁亮屏闲置、省电关闭。电池 80% → 81%、37.8°C → 38.1°C，测量前后系统热状态均为 0；没有连续采样热状态。
- 同前一有效并发扫描相同的压缩 APK：SHA256 `248e5f9f7f5a0974df16f0a78c316cfa4210bee226a67431696f87a6e2012d9c`；源码指纹 `270cef4f47d6e3f4a22a60fbdb77608eeaae1556b0d027eb0341d528443fb970`。

ADK 使用真实 `InMemoryRunner`、`LlmAgent` 和新 Session，自定义 Model 使用 FitLog 原始传输；修复的空白 user turn 桥接也已获得本次实机线上证据。没有验证 ADK 内置 Google provider，也不是第三方仓库原项目的速度成绩。原生 APK 本轮构建通过；26 个 Kotlin 和 15 个 Python 测试是此前该源码版本的验证记录，本轮没有重复跑未改动的测试。

## 实测结果

| 配置（并发均为 2） | HTTP 尝试 | 检查点通过 | 八篇整批耗时 | 首个持久化且可核对候选 | 有效候选/分钟 |
| --- | ---: | ---: | ---: | ---: | ---: |
| ADK 1.3.1 canonical-model bridge | 8 | 8/8 | 59.985 秒 | 7.752 秒 | 8.002 |
| 轻量 Kotlin | 8 | 8/8 | 75.963 秒 | 5.600 秒 | 6.319 |

两者均完整完成，无质量失败、请求失败或未执行。ADK 比本次配对轻量批次少 15.978 秒，即整批耗时下降约 **21.0%**；首个可核对候选反而晚约 2.152 秒。这个差值不能用前一次轻量 c2 的 62.974 秒替换参照，也不能将不同实验阶段凑成独立配对时段。

请求正文 SHA256 逐篇在两种 runtime 中完全相同，也与有效并发扫描一致。每个 profile/日记只有一次 HTTP 尝试，本轮请求号为 1–16；最大被 benchmark 接纳的在途尝试均为 2。ADK 每篇一个 runtime 事件，共八个；工具调用为零。事件序列、响应保存、来源哈希与终止计数完整。

合计 16,668 输入、13,074 输出 tokens；缓存输入已经包含在输入中。没有 provider 单价或推理 token 分解，不把所报输出 tokens 当成可见 JSON 长度。HTTP 含引擎排队、网络与完整响应，不能拆成服务端推理耗时；连接允许复用但没有观测实际连接 ID。

runtime 阶段是相应计时边界的墙钟残余，不是 CPU profiling。ADK 观测到的初始化与其余 runtime 阶段合计约 123 毫秒，轻量约 59 毫秒；它们不能解释为“ADK 框架自身节省了 16 秒”。阶段在并发任务间重叠，也不能简单相加作为整批时间。

两批最后完成的是同一篇复杂训练记录：ADK 配额等待 27.050 秒、HTTP 32.838 秒，轻量分别为 34.098、41.811 秒，Provider 所报输出 tokens 为 2,093 / 2,748。完成关键路径、请求接纳顺序、模型响应和缓存存在差异，现有观测不能把全部批次差值归因于 runtime。堆内存只保存结束快照，不用于宣称峰值或内存优势；八篇 p95 仅作描述。

## 质量与收尾核验

两种 runtime 的空文与四篇普通记录均没有训练动作。三篇训练/混合记录保留了原文的动作名称；已知重量、单位、组数和次数通过冻结检查点。缺失数据与 UNKNOWN 保留；尾部加号的不完整次数在两者中都保留已记录的 6、8，组数未知并附核对问题。没有把候选写为用户确认数据。本次空文通过也不能说明历史偶发编造已解决。

有限抽查与回答文件指纹在 `manual-quality-review.json`，未改写原检查点分数。全部 173 篇原文及目录清单与冻结指纹一致；源码、报告和设备临时凭证核验没有发现 Key，扫描数见 `measurement-validation.json`。生产调度、原文及用户确认修正未改动，没有暂存或提交。

本次读取嵌入的冻结快照，host 前后核对原文件；未经过 SAF，未验证生产 UI 帧率、真实用户点击取消或完整 173 篇批次速度。取消生命周期的既有离线证据见 [RESULTS.md](RESULTS.md)，没有把离线结果冒充本轮在线取消测量。

## 选型与下一时段

本轮增加了 ADK 自定义桥接的真实 Android 可部署、协议一致性和有限质量证据。只有一个有效配对时段，`paired_batch_intervals.adk-c2-vs-lightweight-c2=null`，速度门槛未通过，`final_winner=null`。因此继续保留直接调用/轻量 Kotlin 为默认；并发 2 仍是前一曲线的探索性建议。

下一时段仅准备了 `out/native-ready-runtime-c2-period-2/plan.json`：同源码、并发 2、同八篇，种子 44，配置顺序为轻量、ADK，前序实际计数 108、上限 16。准备没有读取凭证或发请求，实际执行要在另一个闲置时段。不同 `--period` 名称本身不构成独立测量，不把同一窗口内的 `--rounds` 重复当成独立时段。

至少再补两个真实独立配对时段才能输出初步 95% 区间；更可靠的结论需要更多时段。并发曲线也需要独立重复，并用入围配置验证完整目录。复杂 runtime 仅在部署与质量通过、配对速度提升区间下界超过 10% 且集成成本可接受时凭性能获选。后续正式测量不自动启动，不自动调用剩余额度。
